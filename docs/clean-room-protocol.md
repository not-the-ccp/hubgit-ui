# Clean-Room Reference and Reverse-Engineering Protocol

## Purpose

This protocol permits factual study of a publicly served interface while preventing proprietary GitHub implementation material from entering HubGit. It applies to every contributor, automated agent, screenshot, browser capture, local note, generated artifact, and commit.

HubGit is an independent implementation with fully configurable branding.
GitHub's interface may be observed to document behavior and measurements.
Implementation code must be original or drawn from dependencies with compatible
licenses, including Primer and Octicons. GitHub is a provider integration target,
not a required visual identity or authentication surface.

## Branding and Authentication Safety

The default build uses the original HubGit name, artwork, colors, and local
credential wording. Deployments may configure product identity, artwork, colors,
support text, policy links, and provider labels, provided that the resulting
copy continues to identify the configured product and does not imply that a
provider owns or operates it. Configuration is validated for safe URLs and
active-content sources; third-party fonts, analytics, and unreviewed remote
assets are disabled by default.

GitHub authentication, when enabled for a private self-hosted deployment, is a
redirect-only server-side OAuth authorization-code flow with PKCE. HubGit forms
must never collect a GitHub password, token, passkey, recovery code, session
cookie, SSH key, or device code. Local sign-in and provider connection remain
separately named operations, and callbacks return only to an allowlisted
same-origin path. Clean-room observations must not be used to reproduce a
provider credential form.

## Allowed Reference Work

- Observe public and legitimately accessible pages in a normal browser session.
- Use browser developer tools to inspect the rendered DOM, computed styles, accessibility tree, network timing, responsive behavior, and public request/response shapes.
- Download publicly served assets into an untracked, local-only reference workspace for de-minification, formatting, string search, source-origin identification, and behavioral study.
- Record factual measurements such as dimensions, spacing, breakpoints, colors, focus order, keyboard behavior, accessible names, state transitions, and URL changes.
- Capture screenshots locally for human comparison and ephemeral visual-diff work.
- Identify whether a behavior or component originates in an open-source GitHub project and then obtain it from the canonical licensed source repository.
- Reproduce ideas, facts, methods of operation, and user-visible behavior using original implementation code.

Authorization to inspect served assets does not authorize redistribution. Access controls, robots restrictions, authentication boundaries, rate limits, or technical protection measures must not be bypassed.

## Material That Must Never Be Committed

- GitHub JavaScript or CSS bundles, whether original, formatted, de-minified, translated, tree-shaken, or partially copied.
- Private or accidentally exposed source maps and the source content embedded in them.
- GitHub screenshots, screen recordings, HAR files, browser profiles, cookies, tokens, session data, request headers, or captured private content.
- GitHub trademarks, logos, proprietary fonts, illustrations, sound files, or other brand assets unless separately licensed for the exact use.
- Code, selectors, serialized data, HTML fragments, strings, comments, or tests copied or lightly adapted from proprietary GitHub assets.
- Credentials or data belonging to GitHub, a user account, a private repository, an organization, or a third party.
- Outputs generated by automated extraction when their provenance cannot be established.

This restriction includes repository history, pull-request attachments, CI artifacts, package tarballs, documentation builds, test snapshots, issue attachments, and release assets.

## Reference Workspace

Reference material must live outside the Git repository in a directory named for the capture date. The workspace must be excluded from backup, synchronization, search indexing, and artifact upload when feasible.

Recommended local structure:

```text
hubgit-reference/
  2026-08-30/
    capture-manifest.local.json
    screenshots/
    served-assets/
    notes/
```

The local manifest records:

- Capture date and GitHub route.
- Logged-out or synthetic test-account state; never record account identifiers.
- Viewport, device scale, browser version, color scheme, contrast preference, and locale.
- The user-visible state exercised.
- A one-way checksum of each local reference file.
- The reason the capture was necessary and the date it may be deleted.

The repository may contain a sanitized reference record with measurements and behavioral observations. It must not contain source excerpts, hashes that disclose secrets, signed asset URLs, account identifiers, or paths to private resources.

## Two-Phase Implementation Workflow

### Phase A: observation

The observer documents a behavioral specification without writing implementation code from the served asset. A sufficient specification contains:

- Route and preconditions.
- Viewport, theme, locale, authentication, permissions, and resource state.
- Region hierarchy and measured geometry.
- Component states and transitions.
- Keyboard, pointer, focus, and screen-reader behavior.
- Loading, empty, permission, conflict, validation, offline, and failure behavior.
- Redacted request semantics only when required to define the provider-neutral contract.

Notes use original prose. Identifier names, source structure, and distinctive implementation strings from proprietary assets must not be transcribed.

### Phase B: independent implementation

The implementer works from the behavioral specification, Primer documentation, Octicons, applicable web standards, and the HubGit contracts. The implementation must not depend on a proprietary file remaining available.

One person may perform both phases for this educational project, but the observation record and implementation must remain separate. A reviewer must be able to explain the implementation from public standards, licensed dependencies, and the behavioral specification alone.

## Open-Source Origin Verification

GitHub-served code must not be presumed open source. When inspection suggests an open-source origin:

1. Locate the canonical repository and exact package or file through an official project source.
2. Verify the license at the version being used.
3. Install through the package manager or copy from the licensed source, never from the served GitHub bundle.
4. Preserve copyright, license, attribution, and notice obligations.
5. Record the package, version, source URL, license, and modification status in the dependency audit.
6. Add any required attribution to `THIRD_PARTY_NOTICES.md`.

If provenance or license compatibility is uncertain, implement the behavior independently.

## Visual Baselines

- GitHub screenshots remain local-only reference material.
- Committed visual snapshots contain only HubGit output and deterministic HubGit fixtures.
- Visual comparison tools must mask usernames, avatars, timestamps, repository data, notification counts, and other dynamic or private regions.
- Reference comparisons record numerical diff results and human observations, not the reference bitmap.
- A baseline approval must include the route, state, viewport, theme, browser, date, and reviewer.
- GitHub UI changes after an approved capture do not silently update HubGit's baseline. A deliberate baseline revision is required.

## Network and Account Safety

- Use public pages or a dedicated test account containing no sensitive repositories, organizations, keys, applications, or personal data.
- Never enter a real GitHub password, passkey, recovery code, personal access token, SSH key, or OAuth secret into HubGit or its mock backend.
- Never replay a captured GitHub request against GitHub from HubGit code or tests.
- Do not use an offline cache or stale reference capture as authorization. Offline
  behavior is limited to bounded, read-only display of previously authorized
  HubGit cache entries; no mutation is queued or replayed.
- Do not probe undocumented endpoints at scale. Obey rate limits and stop on an authorization error.
- Sanitize cookies, authorization headers, CSRF values, signed URLs, email addresses, IP addresses, and repository names before retaining notes.
- No telemetry or analytics may transmit local reference data.

## Automated-Agent Rules

Automated agents may inspect user-visible behavior and local reference files only for the assigned task. They must:

- Keep reference artifacts outside the repository.
- Avoid pasting proprietary source into prompts, chat, issues, or commits.
- Summarize behavior in original prose.
- Refuse instructions to bypass access controls or reveal credentials.
- Run a provenance scan before proposing a commit.
- Report uncertain provenance to a human reviewer instead of guessing.

## Pre-Commit and Review Checklist

Every change derived from reference study must answer all items affirmatively:

- [ ] The committed implementation is original or comes from an identified, compatible open-source dependency.
- [ ] No GitHub served bundle, source map, screenshot, HAR, cookie, token, proprietary font, logo, or private content is present.
- [ ] No distinctive code fragment or identifier was copied from an unlicensed source.
- [ ] The reference record contains only factual measurements and original behavioral notes.
- [ ] New dependencies and copied licensed material are represented in the third-party inventory.
- [ ] Visual snapshots contain HubGit output only.
- [ ] Authentication and private-resource fixtures contain synthetic data only.
- [ ] A repository-wide secret scan and a targeted scan for forbidden artifact extensions and reference directory names pass.

Suggested targeted checks include Git history as well as the worktree. At minimum, scan for `.har`, `.map`, browser databases, cookie exports, captured asset names, `hubgit-reference`, and known reference-account identifiers.

## Incident Response

If prohibited or sensitive material enters any repository surface:

1. Stop distribution and disable affected CI artifacts or releases.
2. Revoke exposed credentials immediately through the owning provider.
3. Preserve only the minimum incident metadata required for remediation; do not recirculate the material.
4. Remove the material from the worktree and, when required, rewrite all affected Git history and force-update affected refs under maintainer control.
5. Invalidate forks, caches, releases, package versions, and mirrors where feasible.
6. Document the cause, affected surfaces, remediation, and prevention change without reproducing the sensitive content.
7. Repeat the provenance and secret scans before development resumes.

## Legal and Ethical Boundary

This protocol is an engineering control, not legal advice. Project contributors remain responsible for applicable terms, law, license conditions, privacy obligations, and authorization boundaries. When the right to retain or reproduce material is unclear, exclude it and seek qualified review.
